# M5：控制台、9router 管理、模型路由、共享限流

M5 保留原有请求体与 SSE 透传，默认仍可单进程、无 Redis 运行。控制台入口是状态端口的 `/console`，例如 `http://localhost:8091/console`。用 `server.admin_token` 登录；`/` 仍是只读状态页，`/dashboards` 保留 opener token 权限。

## 控制台

Jinja2 服务端渲染，Bootstrap 5.3.3 放在 `app/static/vendor/`，运行时不依赖外部 CDN。提供：

- 总览：费用、队列、并发、额度刹车、账本和共享协调健康。
- 池与规则：全部规则及其模型作用域，临时收紧、解除金额限制和撤销覆盖。
- 用户：跨 key、跨池的费用、排队、并发及规则。
- 9router：同步、健康、连接、模型、combo、模型路由检查、额度、输出 token 对账，Dashboard 入口开关。
- 价格、用量、事件和配置重载。

登录使用签名会话 Cookie（HttpOnly、SameSite=Strict、8 小时），表单及 Cookie 管理 API 校验 CSRF。Bearer 管理 API 可继续供 CLI 使用。原始管理员 token 不保存在浏览器 Cookie 中；管理员 token 改变会让原会话失效。多进程/副本必须设置相同的 `SECRET_KEY`；HTTPS 部署设置 `LINGQU_SECURE_COOKIES=1`。

Dashboard 反代过滤控制台会话及 opener Cookie，并拒绝上游覆盖这些本地 Cookie。

配置仍以 YAML 为来源。修改数据库 DSN、Redis 连接或监听端口需要重启。控制台的配置页只展示规则和运行参数，不展示 key、管理密码或带凭据的 DSN。

## 模型路由与规则

```yaml
pools:
  - name: claude
    kind: claude
    upstream: router
    priority: 0
    match: {models: ['claude-*', 'cc/*']}
    rules:
      - {kind: hourly_cap, limit: 20}
      - {kind: hourly_cap, scope: {model: '*opus*'}, limit: 8}
      - {kind: concurrency, max: 3, on_exceed: hold}
      - {kind: rpm, scope: {model: '*opus*'}, max: 10, on_exceed: reject}
  - name: codex
    kind: codex
    upstream: router
    match: {models: ['gpt-*', 'cx/*']}
    rules: []
keys:
  - {key: '${LQ_SHARED}', upstream_pools: [claude, codex], unmatched: reject}
```

规则如下：

1. 专用 `pool` key 直接进入绑定池；`upstream_pools` 中的池必须属于同一上游，且都配置 `match.models`。
2. 匹配使用原始请求模型名、区分大小写的 shell glob（`*`、`?`、`[]`）；不隐式去前缀，不改写模型或请求体。combo 名称也需要显式匹配。
3. 多池命中时，较大的 `priority` 优先。最高优先级仍有多个匹配时返回 400；不按 YAML 顺序选择。相同优先级的完全相同模式在加载时即报错，其他交叉模式在请求和管理器路由核对时发现。
4. 未命中默认 400。`unmatched: fallback` 要求同一绑定中的 `fallback_pool`；显式 `unmatched: unknown` 恢复旧的仅计量 unknown 池行为。升级已有共享 key 时需注意这一默认行为变化。
5. 池级规则和所有命中的模型作用域规则一起执行，`hourly_cap`、`hourly_budget`、`cycle_cap`、`concurrency`、`rpm` 均支持 `scope.model`。`/status` 的 `rules` 展示每条规则的实际计量。新增模型金额作用域会读取已有模型历史；新增并发/RPM 作用域会计入在途/最近请求，不会在热重载时获得空白额度。
6. 同一池内 enforcing 小时规则的 release 和 session_aware 必须一致。shadow 只记录，不阻止请求。

费用按响应实际模型定价，规则按**请求模型**归集。这样一个经过定价的别名/combo 即使返回其他模型名，也会计入请求所命中的规则；重启恢复采用相同口径。

`GET /v1/models` 和 count_tokens 等非计费端点继续透传。共享 key 的模型拒绝策略和用户限流作用于三个计费推理端点。

## 用户级限流

```yaml
users:
  - name: alice
    rules:
      - {kind: hourly_cap, limit: 10, on_exceed: reject}
      - {kind: rpm, max: 30, on_exceed: reject}
      - {kind: concurrency, max: 2, on_exceed: hold}
      - {kind: cycle_cap, cycle_limit: 200, cycle_period: 7d, anchor: 'mon 00:00'}
keys:
  - {key: '${ALICE_CLAUDE}', pool: claude, user: alice}
  - {key: '${ALICE_CODEX}', pool: codex, user: alice}
```

同一 `user` 的所有 key、所有池共用用户额度。身份只来自服务端 key 绑定；客户端的 `user`、metadata、会话 ID 和自定义头不能切换身份。未绑定用户的旧 key 保持仅池级限流。

池和用户在同一个准入临界区一起判断：两者都允许才占用名额和 RPM；不会因用户被拒绝而消耗池的 RPM。金额计量也一起提交，流开始和结束的计量方式保持不变。排队仍受 max_queue/max_hold、金额放行间隔和并发约束控制，超限使用项目原有的协议兼容 503。

用户规则支持 hourly_cap、cycle_cap、RPM、并发、模型作用域和 shadow。用户不对应单个订阅，因此 hourly_budget 只用于订阅池；用户 cycle_cap 需显式指定日历或 Unix anchor。内部用户统计池为 `@user/<name>`，配置不允许普通池使用此保留前缀。

迁移 `0004` 增加 `ledger.user_ref` 存储可信身份；原 `user_tag` 仍只记录客户端标签。单实例恢复会重建用户费用、周期历史、会话与最近一分钟 RPM；`/stats` 新增 `users` 汇总。旧账本不会把客户端标签提升为可信身份。

## 9router 管理器

每个需要纳管的上游配置：

```yaml
upstreams:
  - name: router
    base_url: http://9router:20128
    api_key: '${ROUTER_KEY}'
    manager: {password: '${ROUTER_PASSWORD}', refresh: 3m}
    quota: {password: '${ROUTER_PASSWORD}', refresh: 3m, stale_after: 6m}
```

管理适配器通过 `/v1/models`、`/api/providers`、`/api/combos`、`/api/pricing`、`/api/usage/<id>`、`/api/usage/history` 同步。连接字段采用允许列表；不保留 OAuth token、providerSpecificData 或可能以完整 API key 为键的 byApiKey。失败保留上次库存并标记 stale，各端点失败单独报告。后台和手动同步串行；连接失效/过期、不同实例出现同一 OAuth connection ID 会告警。不同 ID 对应同一真实账号时不能据此识别，仍需部署方核对。

输出 token 对账采用两次同步间的增量，至少观察 10 分钟、至少 1000 个输出 token；超过 10% 提醒核对直连和计量覆盖。使用上游 usage 总量与本地可信 usage 账本，不把两边不同价格口径的美元数直接比较。采样边界和账本延迟会影响结果，对账是排查线索。新实例/上游计数回退时重新建立基线。

管理器负责检查和同步库存；OAuth 授权、连接编辑、key 轮换和 9router 自身的数据备份通过原生 Dashboard 入口执行。它不会复制 OAuth 连接、挂载 Docker socket、执行容器命令或自动升级 9router。所有读 API 都与 Dashboard 是否开放独立。

适配依据：[providers](https://github.com/decolua/9router/blob/master/src/app/api/providers/route.js)、[combos](https://github.com/decolua/9router/blob/master/src/app/api/combos/route.js)、[usage](https://github.com/decolua/9router/blob/master/src/app/api/usage/history/route.js)。不同版本缺少端点时控制台会报告该项失败。

## Redis 多实例

```yaml
redis:
  url: '${LINGQU_REDIS_URL}'
  namespace: lingqu-prod
  lease: 90s
  socket_timeout: 3s
storage:
  dsn: '${LINGQU_DATABASE_URL}' # postgresql+psycopg://lingqu:password@postgres/lingqu
```

- 同一个部署使用同一个 Redis、namespace、SQL 数据库和相同配置，副本时钟需要通过 NTP 同步。不同部署使用不同 namespace。
- Redis 保存滚动窗口、32 天模型费用历史、全局队列、出队时刻、会话、RPM、并发租约、覆盖规则、额度及预算缓存。一个带所有权校验的短事务同时更新池和用户；等待与上游转发在锁外执行。锁过期的写者不能提交旧状态。
- 流式请求每 10 秒续租，默认租约 90 秒。进程崩溃后名额与队列项最晚在租约到期、下一次访问时回收。超过租约长度的进程暂停/网络分区可能让仍在上游运行的请求失去名额，租约应长于部署允许的最长故障暂停。
- 跨副本最多约 250 ms 重新检查队列；同进程仍可由 Condition 提前唤醒。每个副本的线程容量需要容纳分配给它的长流与排队请求。
- Redis 故障或配置指纹不一致时拒绝新的计费准入，返回 503；不会切换到独立本地计数。`/healthz` 返回 503 并给出协调异常，控制台提供故障页与本实例重载按钮。
- `LINGQU_WORKERS` 可以大于 1；未配置 Redis 时启动配置明确拒绝多 worker。每个进程独立处理 HTTP 连接、写本地待写账本队列和执行后台任务。数据库应使用共享 PostgreSQL，驱动已包含在锁文件中。
- Dashboard 入口状态以共享 SQL 为准，修改和过期检查由 Redis 串行；关闭入口立即影响所有副本。9router 登录 Cookie 和失败后的 30 分钟冷却也在副本间共享。
- 滚动窗口和周期计数直接从 Redis 使用，启动时不再次回放 SQL 账本，防止每个副本重复加钱。需要开启 Redis AOF、持久卷和 noeviction。示例 `appendfsync everysec` 在主机故障时存在约 1 秒持久化窗口，参见 [Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。Redis 数据完全丢失不会自动从 SQL 合并恢复：应停止所有副本，恢复 Redis 备份后再启动。
- 当前使用单个命名空间状态文档与短全局锁，适合项目预期的低请求率订阅网关；序列化开销随 32 天历史增长。未宣称适用于高吞吐服务，也未实现 Sentinel/Redis Cluster 故障转移协议。
- 配置重载需要发到**每个实例/worker**，或通过相同配置协调重启。第一个实例应用新配置后，尚未重载的实例会拒绝计费准入，防止按不同规则放行。通过负载均衡器反复调用一次 reload 不保证命中所有 worker。建议变更时先摘流量，完成所有实例更新后恢复。
- 定价/管理器库存、线程心跳、待写账本延迟和错误连续次数属于各 worker；SQL 统计和限流状态属于全局。管理器库存重启后重新采集。

### 双副本示例

`compose.redis.yaml` 包含 Redis AOF、PostgreSQL、单独迁移任务、两个灵渠副本和 Nginx 入口。迁移完成后才启动副本，避免并发建表。Nginx 关闭 SSE 缓冲和自动重试，动态解析副本地址。示例暴露代理 8090，管理 8091 和一个 Dashboard 端口 8101 仅绑定宿主机回环；更多 Dashboard 端口需扩展 Nginx 和端口配置。

准备 `.env`：

```dotenv
POSTGRES_PASSWORD=replace_with_random_password
LINGQU_DATABASE_URL=postgresql+psycopg://lingqu:replace_with_url_encoded_password@postgres/lingqu
LINGQU_REDIS_URL=redis://redis:6379/0
SECRET_KEY=replace_with_a_shared_random_session_secret
LINGQU_ADMIN_TOKEN=replace_with_random_admin_token
# 其他 lingqu.yaml 引用的上游变量也放在这里
```

配置 `lingqu.yaml` 的 redis、storage 及实际可达的上游地址，再运行：

```bash
docker compose -f compose.redis.yaml config --quiet
docker compose -f compose.redis.yaml up --build -d
# 管理入口：http://127.0.0.1:8091/console
```

这是部署模板；需要按实际网络、上游端口和密钥填写，不能直接使用 example 中的占位地址。

## 接口及验证

新增管理员接口：`GET /admin/routers`、`POST /admin/routers/<upstream>/sync`、`GET /admin/users`、`GET /admin/routing?model=...`。路由检查不返回原始 key。CLI：`flask router list`、`flask router sync <upstream>`；`flask check` 会检查 Redis 连通性。

升级前备份数据库，安装锁定依赖并执行 `flask deploy`。测试：

```bash
.venv/bin/python -m unittest discover tests -v
```

`tests/test_m5.py` 包括真实 Redis unix socket 集成测试：多进程竞争、跨实例排队、租约续期/回收、配置不一致、故障拒绝和过期写者校验。找不到 redis-server 时该组明确 skip；其余测试不依赖外部 9router。生产上游适配仍需用 `flask check`、管理器同步和 shadow 规则核对。
