**Lingqu 深入分析与优化方案 · 2026-10-22**

结论：Lingqu 的定位和主要设计适合 MachGate 当前的小规模订阅共享场景。最值得保留的是按池隔离、原始请求/SSE 透传、输入费用提前计入、有限等待和回放工具。当前第一优先级是计量与故障处理的正确性，其次是将已经实现的额度能力接入实际配置，最后才是分布式扩容和框架迁移。

本次评审基于 Lingqu 提交 `7b7606e` 的本地源码、MachGate 配置生成器及部署文件。没有查询生产集群、真实账本或实际账户额度，因此不把仓库配置当作已验证的线上状态，也不声称已经测出真实节省比例。未修改应用代码或部署配置。

**一、先分清已经实现的能力与部署接入程度。**

请求路径是 `New API → key 绑定/协议识别 → 池与用户联合准入 → 9router → SSE 透传及 usage 计量 → 窗口更新/异步账本`。控制线程负责价格、额度、管理器、快照和告警。

[MachGate 配置生成器](../../../scripts/machgate.py:667) 目前生成的是：每组每 provider 一把 key、固定 `hourly_cap`、FIFO、SQLite、`fail_mode: open`、每池队列 8、缓存请求等待上限 120 秒、最大等待 150 秒。价格由外部同步任务复制为 static，webhook 为空；没有生成 Redis、quota、manager、users、并发限制、动态小时预算或 session-aware 配置。仓库中的三组 Claude 小时阈值均为 20 eUSD，Codex 未设置对应金额阈值。[部署文件](../../../deploy/k8s/lingqu.yaml:29) 则是单副本、Recreate、1 GiB 内存上限。

因此，M4/M5 的大部分能力目前属于“实现可用、接入链路尚未体现”。直接编辑生成的 YAML 会被下一次 apply/sync 覆盖。优化必须贯穿 `groups.toml → 校验 → render_lingqu → reload/check → 状态展示`。

还有一个身份约束：现有 key 代表渠道/池，不能识别同一渠道下的不同自然人。增加 `users` 配置本身不能实现按人限流，需要 New API 到 Lingqu 之间传递可验证身份，例如服务端映射的用户专用 key，或者受信且可校验的身份声明。客户端可写的 user/session/header 不能承担鉴权。

**三、预算控制的实际语义需要明确：hourly_cap + hold 是软降速阈值。**

[Gate._money_decision](../../app/gate/hold.py:315) 在等待达到 hold cap 后允许 `released_by_cap`，再交给并发/RPM 限制判断。因此当前的 20 eUSD/h 并不保证任意滚动小时不超过 20。它优化的是等待、缓存命中和消耗速度之间的折中。现有迁移文档也明确承认 FIFO 压不住硬峰值。

同时，准入只看到已经计入的费用，没有在途请求的预算预留。示例：已计费 19，3 个尚未返回输入 usage 的请求各消耗 4，在没有并发限制时都可能先获准，随后总额升到 31。这里的数字是说明机制的假设，不是线上测量。

小时预算、缓存截止时间、有限排队和零拒绝无法在任意高负载下同时保证；新增功能应该明确冲突时的优先级：

1. 保留软平滑模式，用于正常使用体验；控制台名称改成“小时降速阈值”，展示实际峰值、超额面积及 cap 强制放行比例。
2. 独立定义资源保护规则：并发、RPM、周期额度和上游额度刹车。保护规则触发时允许拒绝，不让“缓存将过期”覆盖资源保护。
3. 先以 shadow 方式计算 `effective_spend = observed_spend + reserved_spend`。预留按池、模型、可信会话、冷/热状态的历史分位数估计，在 message_start/最终 usage 到达时结算差额。
4. 上线预留前验证误差和缓存重建代价，设置可解释的有限透支/欠额偿还策略。估计不能带来绝对硬限额保证；若需要严格金额边界，必须结合请求成本上界、可控输出上限和拒绝策略。
5. 不直接用“预估费用越大、下一请求等待越久”的简单令牌桶替换 FIFO：仓库回放已经指出这种做法可能增加缓存重建。热请求截止时间、用户公平和冷请求等待应共同参与调度。

建议先观察每池并发 2/3 的 shadow 对比，再决定 enforce。该数值是试验候选，不能仅根据现有代码宣布最优。

**四、计量数据还需要质量分层与持久化闭环。**

[无最终 usage 的退化路径](../../app/proxy/views.py:215) 会按已发送原始字节数除以 4 估算 output；拿不到 input_ready 时把输入清空。对于没有 include_usage 的 Chat SSE 或中途终止的 Responses，输入费用可能漏计；原始字节还包含 SSE/JSON 开销，压缩时又会低估明文输出体积。这不能当作统一方向、统一比例的保守估计。

保留透明转发承诺，默认不要擅自给请求加 stream_options。改进顺序是：监测 upstream/estimated/none 占比与费用占比；部署方配置支持 usage 的客户端；不完整流在解析副本上估计有效输出内容，输入单独给出估计和置信度；对无法计量的协议提供显式策略。未知价格/default-price 也应进入同一质量面板。

当前账本只在响应结算后进入内存队列，最多约每秒 flush；输入虽然提前 charge，却要等周期快照或最终账本才持久化。崩溃窗口中的在途输入无法保证恢复。[restore](../../app/runtime.py:178) 出错只记录 warning，并没有将“恢复未完成”作为 readiness 条件。Redis 模式则直接信任 Redis，不从 SQL 重放。

建议增加 request_id、计量事件序号、价格版本、模型/账户归属、observed/committed 状态和幂等约束；让恢复基于事件水位而不只依赖 wall-clock 时间戳。单实例可先采用有界本地持久 journal，集中数据库则使用适合其事务模型的事件表/outbox，分别验证 SIGKILL、SQL 不可写和提交应答丢失。持久化事件只能保证已观察到的 usage；上游尚未报告的真实消耗仍需保守估计和事后对账。明确定义 RPO，再决定 fsync/批量策略。

还需增加 readiness 的初始化/恢复状态。对于 Redis 状态缺失，区分首次空库启动与已有集群丢失状态，使用独立初始化标识/epoch；不能默认把预算当成新周期。自动恢复必须单一执行者和去重，不能让各副本同时重放整本账。

当前价格经外部任务写为 static，[Pricing.stale](../../app/pricing/sync.py:78) 不会把 static 判为 stale。应在生成配置中带上价格源版本、成功同步时间及摘要，并监控外部同步失败，避免展示“价格健康”但实际复制任务长期停摆。

**五、容量保护应先于增加线程或迁移 ASGI。**

[Gunicorn](../../gunicorn.conf.py:6) 默认一个 worker、64 线程，代理、状态、管理和 Dashboard 共用执行容量。每个长流和排队请求都占线程；`max_queue=8` 是每池/用户限制，不能保证全局线程足够。在读完 body 后才进入 Gate，也意味着被拒绝前已经占用内存。

[请求体上限](../../config.py:14) 默认 128 MiB。[relay](../../app/proxy/views.py:92) 还会完整读取并 JSON 解析。64 个满额请求仅原始 body 理论上就是 8 GiB，已经高于部署的 1 GiB，尚未计入 Python 对象和响应副本。这是容量上界分析，不是已经观察到 OOM。

近期优化：

- 增加全局 active/held/incoming body bytes 上限，并与每池限制一起校验；在大 body 缓冲之前尽可能做入口保护。
- 根据真实请求体 p99/最大合法上下文确定上限，同步入口代理配置；大体量请求使用有界缓冲或临时文件，并限制 SSE 单事件和解压后体积。
- 为健康检查与管理提供实际执行隔离。单纯换端口不能预留线程；单实例内存 Gate 也不能简单再起一个独立管理进程并期望共享内存状态，需要只读快照或 IPC。
- 饱和时能快速返回清晰拒绝，健康端点仍有响应；压测同时覆盖长流、大请求体、多池排队和状态页面访问。

仅当测得长连接/排队数量已经使线程容量成为主要瓶颈，再用 ASGI 改代理外壳。迁移时数据库、同步 HTTP 和锁操作也必须避免阻塞事件循环。现有规模先修生命周期和资源上限更有收益。

**六、Redis 实现适合低负载协调，但目前不能据此推导横向扩容收益。**

[SharedLock](../../app/gate/shared.py:38) 每次最外层进入都 GET/反序列化全局状态，退出再 encode/SET；其中包含 32 天逐次费用历史、窗口、会话、队列、额度和预算。等待请求最多每 250 ms 重检；状态和 health 查询也会进入这个写回事务。

本地纯序列化基准如下，尚未计算网络、Redis 排队与决策本身：

| 历史 charge 点 | JSON 大小 | 单次 encode/JSON/decode 中位耗时 |
|---:|---:|---:|
| 1,000 | 19,261 B | 0.69 ms |
| 10,000 | 190,261 B | 5.25 ms |
| 100,000 | 1,900,261 B | 55.99 ms |

低请求率仍可能积累长历史。如果 8 个等待者各按 4 次/秒检查，就有最多约 32 次/秒的检查需求；在本次 10 万点样本下，仅上述串行 CPU 工作就约需 1.8 秒/秒，实际轮询会因此变慢。该计算说明瓶颈方向，不代表生产 RPS 上限。

建议分阶段处理：先增加状态字节数、锁等待/持有时长、事务 p95/p99、续租延迟的指标，缓存配置指纹并减少不必要写回；再把热准入状态与长历史拆开。Lua/Redis 事务只处理必要的计数、租约和预留；历史采用桶与边界精确点、或独立事件存储。池和用户必须联合原子准入，不能拆成两次先后扣减；任意跨池用户会影响分片方案。唤醒采用通知加超时兜底，不能只依赖可能丢失的通知。

同时处理运维一致性：当前指纹覆盖全部 Settings，第一个实例 reload 后其他实例会拒绝准入；需要版本化配置、各 worker 确认和明确切换流程。quota/manager/pricing 后台任务每 worker 都运行，应引入采集者租约或共享刷新结果，避免副本数增加后重复请求、重复对账和告警。保留现有锁所有权校验与故障拒绝，不要为性能改成各副本独立放行。

Redis 优化验收必须使用真实 Redis 和 PostgreSQL，包含多进程竞争、续租超时、配置切换、响应丢失、状态丢失、进程崩溃及 32 天规模历史；本次跳过的 11 项不能视为已通过。

**七、会话调度与回放应服务于验证，而不是替代验证。**

[SessionClock](../../app/gate/sessions.py:42) 用 `(pool, session)` 和最近发送时间推断缓存。发往上游失败也可能已经把会话标为 warm；同一 session 切换模型/账户、前缀变化、并行子请求都可能破坏该假设。会话 ID 还来自请求字段，不能获得不受约束的插队权。

可以保留该启发式，但要区分 pending start 与 confirmed cache observation，用实际 cache_read/cache_write 反馈修正，并在可获得时纳入模型和真实上游连接身份。调度增加可信用户公平配额、冷请求等待老化、热请求优先的额度上限。缓存 deadline 只约束金额等待，当前并发/RPM 闸门仍可继续阻塞，因此不能承诺所有热请求都保住缓存。

[回放](../../app/replay.py:131) 使用 `ts + held_ms` 作为时间起点，样本又只保留 HTTP status < 400，因此已经被旧策略延迟的流量不能直接视为未经干预的原始到达流。流内错误仍可能是 200。现有模型还假设会话串行、按开始时间差推断缓存，且 current_policy 只提取固定池级 hourly_cap/并发，不能代表完整 M4/M5 联合策略。

改进：记录 arrival/admitted/first_byte/finished 四个时间以及业务任务/重试关联；回放支持明确的“真实到达轨迹”与“观察到的完成轨迹”模式，说明闭环用户行为的假设。尽可能让离线模拟与线上共享纯决策内核，用差分测试保证相同事件下决策一致。合成负载做多种子和敏感性分析；真实池先 shadow、再小范围启用，最终看成功任务、上游额度消耗、等待和缓存重建是否一起改善。

**八、查询与管理面的成本值得随数据量逐步收敛。**

[stats](../../app/observe/stats.py:69) 将时间范围内所有 ORM 行拉入 Python，再多次分组、排序、算并发峰值；30 天查询会与代理共享线程和内存。[QuotaCollector.load](../../app/quota.py:206) 读取全部额度历史。[Manager._reconcile](../../app/manager.py:157) 周期性累计全历史 output tokens；[Manager.sync](../../app/manager.py:103) 持锁执行串行网络操作，snapshot 会等待同一把锁。

优化方向是小时/日聚合表、明确原始账本/事件保留周期、按 `(pool, ts)` 等真实查询模式评估复合索引、额度最新快照、基于水位的增量对账。百分位和并发峰值不能简单平均，需要明确可合并算法或保留必要边界数据。Manager 在锁外采集，在短锁内交换不可变快照，并使用配置版本防止旧任务覆盖新配置。对账延续输出 token 增量，同时增加 cache/input 覆盖质量，避免只看输出正常就误判整体计量正确。

路由方面，专用 pool key 直接进入绑定池，规则按请求模型归集，价格按响应模型选择；它不会根据实际响应自动重分池。[resolve](../../app/proxy/views.py:35) 与 M5 文档一致，但与旧 DESIGN 中部分 combo 描述有差异。应把池内允许的模型/别名/同账户 fallback 写成显式约束，监测 model_req/model_actual 漂移；跨订阅 fallback 应在 9router 配置和校验中禁止，不能事后仅换一个记账池就声称隔离成立。

**九、落地顺序与验收标准。** 以下工期是单名熟悉项目的工程师的粗估，不含线上观察期；阈值是建议的发布门槛，不是现有实测能力。

| 阶段 | 工作 | 建议验收 |
|---|---|---|
| 第 1 阶段，1–2 个工作日 | 三个已复现缺陷；断流/故障分类；补齐必要回归用例 | 任意 chunk 位置关闭后保留已观察 usage；共享计量失败也有结算/待补偿记录；DB 失败 180 秒不能显示 lag≈0；现有 150 项继续通过 |
| 第 2 阶段，3–5 个工作日 | 幂等计量事件/恢复状态、全局容量保护、基础指标；完善配置生成链 | 故障恢复重放不重复计费、不丢已确认持久化事件；符合声明 RPO；饱和时健康检查可达；所有配置变更可 check/回滚 |
| 第 3 阶段，观察 1–2 周 | quota/manager 接入、并发 shadow、预算预留 shadow、价格和 usage 质量 | 按池/协议统计估计与默认价格占比；上游额度新鲜度清晰；固定预算与动态预算并行比较；样本量和请求组合可比 |
| 第 4 阶段，按证据推进 | 单池开启动态预算/适度并发；验证会话优先和公平策略 | 排队 p95、缓存重建成本、真实额度消耗、上游 429/503、成功任务数联合比较；出现回归可独立退回固定预算 |
| 第 5 阶段，确有容量/可用性需求后 | Redis 热状态重构、集中采集/配置分发、必要时 ASGI | Redis 11 项全部执行通过；补故障注入；用成熟历史量压测，不只测空库；协调延迟目标可先设 p99<20 ms，再按部署基线调整 |

建议首批指标：按池和协议的 usage 来源/缺失率、默认价格费用占比、observed/committed/pending 金额、账本最老年龄/成功写入时间/丢弃数、全局 active/held/body bytes、队列等待 p50/p95/p99、released_by_cap 比例、额度采样年龄、缓存重建费用、端到端首字节延迟、Redis 锁和状态体积。无排队情况下额外代理延迟可先沿用现有迁移目标 50 ms，并明确采用 p95 验收；小样本周期不据此宣布普遍收益。

第一批建议提交的变更应集中在流式结算、账本故障年龄和对应回归测试。随后建立可恢复的计量闭环与容量保护，再让动态额度真正接入 MachGate。这个顺序能让后续调参建立在可信数据和可控故障行为上。
